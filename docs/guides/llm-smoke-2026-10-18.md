# 真实 LLM Smoke Test：2026-10-18

## 运行条件

本地运行使用 Groq 的 `openai/gpt-oss-120b`、Node 24.19.0 和 Playwright 1.64.1。Chromium 构建号为 1248。代码基于 `main` 的 `804146b`，第二轮加入了本 PR 的诊断字段。

模型请求通过用户已配置的 Windows 代理。浏览器直接访问 localhost 合成页面，未使用 isolated fallback。两轮都采用默认的 4 个场景，每个场景最多 8 轮，场景集为 `kumo-synthetic-v1`。

## 实测结果

时间均为香港时间。

| 运行 | 时间 | 通过数 | 模型请求数 | 平均轮数 | 单场景平均耗时 |
| --- | --- | --- | --- | --- | --- |
| 原始报告 | 11:27 | 3/4 | 12 | 3 | 3315.75 ms |
| 启用逐轮诊断 | 13:26 | 4/4 | 10 | 2.5 | 2665.5 ms |

两轮中，搜索、标签和面板场景都通过。第一轮的 `details-agent` 失败：4 轮都是点击，首次动作报告 `changed`，随后两次为 `unconfirmed`，最后一次因重复动作而跳过。原始分类为 `planner_failed`，原因是“页面没有进展”。

原始报告缺少 Ref、表格行上下文和每轮完成标记，无法直接还原每次点击的目标。第二轮的 Trace 显示，模型先点击 `agent-prod` 行的 Ref 1，下一轮观察到完成文本后返回 `done`，独立验证通过。

这次改动没有修改 Prompt、重试策略或完成标准。前后两轮的差异不能作为成功率提升的证据。4 个合成场景也不足以估计真实网页上的可靠性。

## 回归验证

新增的模拟模型用例固定点击正确的详情按钮，完成页面后仍继续点击。报告显示，第二轮起 `completionTextObserved` 为 `true`，最终 `fixtureCompleted` 为 `true`，但 Agent 仍因 `no_progress` 失败。这个用例验证了诊断字段和完成标准，不代表第一轮真实模型一定采用了相同决策。

现有独立验证要求继续生效：模型提出 `done`、验证器确认页面状态和文本、最终 DOM 匹配目标，任务才算通过。

## 复现

在本机配置 `.env.local` 和所需代理后运行：

```powershell
npm run eval:llm -- --trace=true --report=test-results/eval/llm-diagnostics.json
```

代理配置见[本地接入指南](free-llm-api.md#windows-powershell-代理)，字段说明见[评测指南](browser-agent-eval.md#diagnose-a-failed-model-run)。报告留在 Git 忽略的目录中，API Key 和完整模型响应均未写入本文。
